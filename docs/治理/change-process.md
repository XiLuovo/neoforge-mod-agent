# Change Process

本文件定义较大改动时的轻量 spec-driven 流程。目标是让项目长期优化时不跑偏。

## 工作纪律

- 证据优先：关键判断基于代码、测试、文档、trace、报告和命令输出，不基于猜测。
- 先理解再动手：非琐碎任务先读相关调用链、数据契约和现有测试，再改代码。
- 不假装验证：没跑过的测试、没生成过的 evidence、没确认过的现象，不能写成已验证。
- 不反应式叠补丁：同类修复连续失败 2 次后，暂停继续乱试，回到根因分析；连续失败 3 次仍无法确认方向时，向用户说明现象、已排除项、风险和下一步选择。
- 低风险小改不过度仪式化，高风险改动必须先把范围、风险和验证讲清楚。
- 实施中不偏离已确认方向；如果发现更好的方向或必须扩大范围，先说明并等待用户确认。

## L1 任务契约

对 L1 任务，建议先用下面的轻量任务契约收口：

```md
## Goal
本次要解决什么问题。

## Non-Goals
本次明确不做什么，尤其是不改变哪些主线边界。

## Scope
预计修改哪些源码、测试、文档、examples 或 scripts。

## Risks
可能影响哪些 CLI、trace、evidence、benchmark 或公开叙事。

## Validation
准备用哪些测试、命令、报告或 `.agent` 文件证明完成。
```

## L2 Proposal

L2 变更必须先给 proposal 摘要，等用户确认后再实施：

```md
## Why
为什么现在要做，它解决哪个项目短板。

## What Changes
准备改哪些模块、文档、测试或示例。

## Non-Goals
明确不做什么，尤其是不改变项目定位、不绕过确定性 gate。

## Impact
影响哪些 CLI、trace、evidence、benchmark、README 或公开叙事。

## Validation
准备用哪些命令、测试或 `.agent` 证据验收。
```

若后续建立 `OpenSpec/` 或更完整的治理目录，L2 变更应沉淀为 `proposal.md`、`design.md`、`tasks.md` 和必要的能力 spec；在此之前，至少要在对话中完成同等粒度的 proposal 审批。

## 任务清单规则

如果为 L2 任务创建了任务清单：

- 实施时完成一项就更新一项状态，不要到最后批量勾选。
- 如果任务清单与实际发现不符，先解释差异再调整。
- 如果实施中发现 proposal/tasks 需要扩大范围，先停下确认。
- 不为了让当前任务成功而牺牲已有行为、项目主线或可验证性。

## 需要暂停确认的信号

出现以下情况时，应先问用户，而不是直接继续：

- 改动会超过当前任务明显范围。
- 原方案需要改成另一种架构。
- 需要新增数据库、向量库、服务端框架、长期运行组件或外部服务。
- 需要改变 CLI 契约、trace schema、benchmark 指标或公开文档定位。
- 需要删除大量已有逻辑或重写核心模块。
- 测试失败原因不明确，继续修改可能扩大问题。
- 有多个方向都可行，但会影响项目叙事重点。
- 需要改动 `workspace/` 里的旧 evidence 或使用 `--overwrite` 重建展示产物。
- 需要把实验能力、旧版能力或 local-only 材料提升为公开主线。

## 协作记录规则

每次较大改动后，应尽量在变更说明中记录：

- 改了什么。
- 为什么这样改。
- 关键代码入口在哪里。
- 如何验证。
- 用户可以重点学习哪一小块。

如果改动涉及新架构、新模块、新算法或关键 bug 修复，应优先写得可读、可讲、可维护，而不是追求炫技。
